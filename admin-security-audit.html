Admin Dashboard — Security Audit

EthixWeb CRM. Admin and staff area only.

Date: 23 August 2026 · Branch deepanshu-branch at commit 35c32b1
How it was done: read all the server code, then ran real requests against a throwaway copy of the app with an in-memory database.
Nothing in production was touched. No code was changed. No passwords or keys are printed in this document.
This report only says what is broken. It does not tell you how to fix it.

The short version

The outside wall is good. Every admin web address checks who you are on the server, not just in the browser. There are no leaked passwords or keys in the JavaScript files. The security headers are set properly. Someone who is not logged in cannot get in.

The problem is on the inside. The app is built around three levels of admin — new admin (must ask permission), trusted admin (can act alone), and super admin (runs everything). We were able to jump from the bottom to the top in one request, in two different ways. Once at the top, we reset the real super admin's password, read it off the screen, and logged in as them — because admins log in with a password only, with no code sent to their email.

Plain summary: any admin account on this system — even the newest, most restricted one — can make itself the owner of the whole workspace, and then take over anyone else's account. The permission system exists, but it can be walked around.

The four ways in, in order of danger

  1. Any admin makes itself super admin. One request. Two different routes to it — one direct, one hidden inside the approval queue.
  2. Super admin takes over the real owner account. Reset their password, read the new one off the response, log in. Admins have no second factor.
  3. Any admin becomes any client or staff member. Either by reading their one-time login code, or by creating a "click to sign in" link for them and clicking it yourself.
  4. An outsider redirects client login links to their own website — because the app guesses its own web address from whoever talks to it first after a restart.

Security findings

Finding 1 of 16 · CRITICAL · Confirmed
Any admin can make itself super admin by changing the spelling of one word

Where: PUT /api/users/:id — the "edit a user" request. Code in routes/users.js and db/setup.js.

What is wrong: The code has a guard that says "you are not allowed to set the super-admin field here". But the guard only looks for that field written one way — isSuperAdmin. The database layer underneath accepts the same field written the other common way — is_super_admin. So the guard checks one spelling and the database accepts both. Send the second spelling and the guard never notices.

How we proved it: We signed in as an ordinary trusted admin and sent the two versions back to back.

First spelling  → 400  "Use the super-admin endpoints to change admin standing."
Second spelling → 200  isSuperAdmin = true

Permissions afterwards:
  canManageAdmins   true      (can now appoint and remove admins)
  canReadAuditLog   true      (can now read the private activity log)
  canDecideApprovals true

We then opened the super-admin-only audit log with that account and it let us in.

Steps to repeat: Log in as any admin. Send an edit request for your own user with the body {"is_super_admin": true}. You get a 200. Check /api/auth/me — you are now a super admin.

What should happen: Only an existing super admin, using the dedicated "change standing" screen, can hand out that power.

What actually happens: Anyone who can edit a user can hand it to themselves.

Why it matters: The entire three-tier admin design stops meaning anything. Every admin is effectively the owner. This is also the first step of finding 3.

What the attacker needs: One logged-in admin account of any level.

Finding 2 of 16 · CRITICAL · Confirmed
The approval queue can be tricked into approving a promotion that looks like a name change

Where: the same edit request, when made by a new (untrusted) admin, plus utils/approvals.js.

What is wrong: A new admin cannot change things directly — their change is parked in a queue for a second admin to approve. Two things go wrong together. First, the same alternate spelling from finding 1 survives into the parked request. Second, the one-line description shown to the approver is written by a function that also only recognises the first spelling — so a request that grants super admin is described as "Change their details". The approver reads a harmless sentence, clicks approve, and the promotion goes through.

How we proved it:

New admin submits    → 202  parked for approval
Summary shown        → "Change their details for Priya Nair (priya.nair@ethixweb.local)"
What is actually stored → {"name":"Priya Nair","admin_trusted":true,"is_super_admin":true}
Trusted admin clicks approve → 200

New admin's permissions afterwards:
  isSuperAdmin      true
  canManageAdmins   true
  canReadAuditLog   true

Steps to repeat: As a new admin, edit your own user with your real name plus the two flag fields. It parks with the innocent summary. Any trusted colleague approves it. You are super admin.

What should happen: A privilege change should be refused outright, or the approver should see exactly what is about to change.

What actually happens: It is stored, described wrongly, and carried out.

Why it matters: The "second pair of eyes" is the app's main safety net for new admins. It can be beaten by wording alone, with one honest colleague clicking a normal-looking button.

What the attacker needs: One new admin account, and one colleague who processes the approval queue.

Finding 3 of 16 · HIGH · Confirmed
An admin can reset the owner's password and is shown the new one in plain text

Where: PUT /api/users/:id with regeneratePassword, and the login handler in routes/auth.js.

What is wrong: Admins can reset anyone's password, and the new password is sent straight back in the response for them to read. Nothing stops an admin from doing this to another admin, including the super admin. Because admins sign in with a password only and no emailed code, that password is everything you need.

How we proved it:

Trusted admin resets the super admin's password → 200, new password returned
Log in as the super admin with it               → 200, no code requested
Session permissions: full super admin

Steps to repeat: Reset admin@ethixweb.local with email sending turned off, copy the password from the response, log in.

Why it matters: The one account that should be out of reach of everybody else is reachable by every peer. Combined with findings 1 and 2, any admin at all gets there.

What the attacker needs: One admin account.

Finding 4 of 16 · HIGH · Confirmed
Admins never get a second login step, and the "two-step sign in" switch does nothing at all

Where: routes/auth.js, and the two-factor setting on the Settings page.

What is wrong: Two separate problems in one place. First, the login code has a branch that says: if the person is an admin, sign them straight in. Everyone else gets a one-time code emailed to them. So the most powerful accounts have the weakest login. Second, the "Two-step sign in" toggle saves a value to the database that no part of the login process ever reads. We searched the whole login path — the setting is never checked. Turning it on changes nothing.

How we proved it:

Admin logs in    → full session immediately, no code asked for
Client logs in   → "requiresOtp: true", must enter an emailed code
Search of login code for the two-factor setting → zero results

Steps to repeat: Turn on two-step sign in for an admin. Sign out. Sign back in with just the password. You are straight in.

Why it matters: Admin accounts are protected by a single password and nothing else — and the seeded accounts all share the same one. Staff and admins believe they have a second factor switched on when they do not. This makes finding 3 far worse.

Finding 5 of 16 · HIGH · Confirmed
Any admin can read anyone's live login code, and see everyone's login history and IP address

Where: GET /api/auth/otp-logs and POST /api/auth/otp-logs/:id/reveal.

What is wrong: Both are open to anyone with the admin role — there is no distinction between a new admin and the owner. The list shows every recent login attempt with the person's name, email address and IP address. The reveal button decrypts the actual six-digit code. Since a client or staff member's login is just password plus that code, an admin who can see the code can finish somebody else's login.

How we proved it:

New untrusted admin lists the codes  → 200, full list returned
New untrusted admin reveals a client's code → 200, code returned
A log row contains: user id, name, email, IP address, time, attempts

Why it matters: Any admin can step into any client or staff account. This is an impersonation tool, and unlike deleting a ticket it is not held for a second signature. It also hands over every user's login IP address.

What the attacker needs: One admin account of any level.

Finding 6 of 16 · HIGH · Confirmed in part
The app learns its own web address from whoever talks to it first, and puts that address in client login emails

Where: utils/appUrl.js, used when building the "click to sign in" link in welcome emails.

What is wrong: There is a setting called APP_BASE_URL that tells the app its real web address. It is not set on this deployment — we checked. When it is missing, the app takes the address from the very first request it receives after starting up, and keeps it for as long as the process runs. That address is then glued onto the front of the one-tap sign-in links emailed to clients.

So: if an attacker is the first to reach a freshly restarted server, and sends a request claiming to come from their own website, every client welcome email afterwards contains a working login link pointing at the attacker's site. The client clicks it, the attacker's server catches the token, and the attacker replays it to log in as that client.

How we proved it:

Sent one harmless request with a made-up source website
Asked the app what it thinks its own address is → "https://evil.example.net"
Created a client → the welcome email link is now built on that address

Why it says "in part": The address poisoning is fully proven. We did not send a real email, because no email service is connected in the test setup. The link-building code path is the same either way.

What the attacker needs: Network access to the server around a restart. No account.

Finding 7 of 16 · MEDIUM · Confirmed
Any staff member can read every client's payment history, even though the page is hidden from them

Where: GET /api/billing/status and GET /api/billing/payments.

What is wrong: The app hides the Billing page from everyone except admins and clients — but that hiding happens in the browser only. The two billing requests behind it check that you are logged in, and nothing more. Anyone who is not a client gets the whole workspace: every payment, amount, currency, card brand and last four digits, and every invoice and receipt link.

How we proved it:

Logged in as an "employee" — the lowest staff role
GET /api/billing/status   → 200, all billing rows for all clients
GET /api/billing/payments → 200, full payment table

Why it matters: This is exactly the mistake of trusting the front end. The company's own design says employees should not see this. The server disagrees.

Finding 8 of 16 · MEDIUM · Confirmed
Any employee can edit or reassign any ticket, including moving it to a different client

Where: PUT /api/tickets/:id.

What is wrong: The handler treats admins, project managers and employees as the same thing — "staff" — and then copies the whole request body onto the ticket. It never checks whether this employee is actually assigned to this ticket. So an employee can change any ticket at all, including the field that says which client it belongs to.

How we proved it:

Employee edits a ticket belonging to Client A,
setting its client to Client B → 200, ticket now belongs to Client B

Why it matters: A ticket can be moved into the wrong client's portal, which shows one client another client's support request. It can also be silently altered or closed by someone with no connection to it.

Finding 9 of 16 · MEDIUM · Confirmed
Any admin can create a "click to sign in" link for a client and use it themselves, with almost no record

Where: POST /api/auth/login-link/:userId.

What is wrong: This is a real feature — an admin makes a link and sends it to a client so they can sign in without typing. Nothing stops the admin from just opening the link themselves. It works for up to seven days. The only trace is a single log line saying a link was issued; everything the admin then does is recorded as the client doing it.

How we proved it:

New untrusted admin creates a link for a client → 200
Opened the link with no login at all            → redirected to the portal
Checked who we were                             → that client

Why it matters: Any admin can act as any client — read their reports, billing and messages, raise or change tickets — and the audit trail will show the client doing it, not the admin.

Finding 10 of 16 · MEDIUM · Confirmed
The audit log does not record that a promotion happened

Where: the logging calls in routes/users.js, read back through GET /api/approvals/audit-log.

What is wrong: When an admin promotes itself using finding 1, the audit log gets one row that says "update, user" with no detail attached at all. A super admin reading the log later cannot tell the difference between someone fixing a typo in a name and someone seizing control of the workspace.

How we proved it:

Admin promotes itself → 200
Newest audit entry: {"action":"update","entity":"user","meta":null,"actor":"A1"}

Why it matters: After the fact, nobody can work out what happened or who did it. Detection and investigation both fail.

Finding 11 of 16 · LOW · Confirmed
The session identifier is not replaced after the login code is entered

Where: middleware/auth.js, the function that upgrades a half-finished login into a real one.

What is wrong: When someone enters their emailed code, the app upgrades the session they already had rather than issuing a fresh one. The same identifier that existed before they proved who they were carries on afterwards. Good practice is to hand out a new one at the moment someone gains access.

How we proved it:

Session id before the code: f0056a85...
Session id after the code:  f0056a85...   (identical)

Why it is only low: The cookie is set by the server and cannot be read by JavaScript, so there is no easy way for an attacker to plant one in the first place. It becomes a real problem only if some other flaw lets them do that.

Finding 12 of 16 · LOW · Confirmed
Uploaded files are not checked, and SVG images are displayed from the app's own address

Where: the Reports upload and download requests, shown on the document page in a frame.

What is wrong: There is no list of allowed file types. Whatever type the uploader claims is what gets stored and later sent back. SVG is on the "show it in the page" list, so an uploaded SVG is displayed inside the app itself rather than downloaded. An SVG is not really a picture — it is a document that can contain code.

The only thing stopping that code running is the security policy header the app sends, which blocks scripts written inside the page. That header is currently correct and does block it. But it is the sole line of defence, and the upload side does no checking at all.

How we proved it:

Uploaded an SVG containing script → accepted, 201
Asked for it to be displayed      → sent back as an image, shown inside the app
Also uploaded a .js file and an .html file → both accepted and stored as-is

Why it matters: If the security policy is ever loosened — a very common change — these stored files turn into code that runs inside the app as whoever is viewing them.

Finding 13 of 16 · LOW · Confirmed
Clients can see the full list of your staff, including who the admins are

Where: GET /api/users, the branch used for non-admins.

What is wrong: Other clients are correctly hidden, but every staff member and admin is returned, with their name, their role, and their internal id.

How we proved it:

Logged in as a client → 200, six people returned, including
  {"name":"Admin User","role":"admin"} and {"name":"Priya Nair","role":"admin"}

Why it matters: An outside customer is handed your internal team list and told exactly which two people are administrators. That is the starting point for a targeted phishing email.

Finding 14 of 16 · INFORMATIONAL · Confirmed
The login response quietly tells you whether an account is an admin

What is wrong: A correct admin password returns a finished session. A correct password for anyone else returns "we have emailed you a code". The two replies look completely different, so anyone testing passwords can tell which accounts are admins — and those are exactly the accounts with no second step.

Finding 15 of 16 · INFORMATIONAL · Confirmed
Login attempts are limited, but sensitive admin actions are not limited separately

What we found: Login is capped at 20 tries per 15 minutes and this works — we hit the wall after 16 attempts. Code entry is capped too, and each code allows only five guesses and expires in five minutes. That part is fine.

What is missing: Sensitive admin actions — revealing login codes, resetting passwords, changing standing — only fall under the general limit of 600 requests per 15 minutes, which is very generous. All limits are counted per IP address, so they depend on the server being configured to trust the right network layer in production, which we could not check from here.

Finding 16 of 16 · INFORMATIONAL · Confirmed
Broken requests return "server error" instead of "bad request"

What is wrong: Send malformed data and you get a 500 "something went wrong" instead of a 400 "you sent something invalid". This is untidy rather than dangerous.

The good part: we specifically checked whether error messages leak anything useful to an attacker. They do not. No stack traces, no database messages, no file paths, no version numbers reach the browser. Attempts at directory traversal were also handled safely.

Things that are simply broken

These are reliability problems, not security holes. Kept separate on purpose.

B1 — Approved account creation loses the Slack channel

What we tried: a new admin proposed creating a client with a Slack channel attached, and a trusted admin approved it.

What should happen: the account is created exactly as it would have been through the direct route.

What actually happens: the approval code copies only some of the fields. The Slack channel is silently dropped, so the client's Messages page never works. We checked the created account: the channel field is empty even though the proposal supplied one.

Priority: medium.

B2 — Approved account creation and password resets never deliver the password

What we tried: a new admin proposed creating a client, and separately proposed resetting a password. Both were approved.

What should happen: the person receives their credentials, or the admin is shown them.

What actually happens: neither. The email is only sent on the direct route, not the approved one. The reply to the proposing admin contains no password either. The account is created, or the password is changed, and then nobody on earth knows what it is. The account is unusable.

We confirmed it twice: zero credential emails after the approved creation, and zero after the approved reset.

Priority: high, for reliability. Onboarding through the new-admin route does not work.

B3 — Duplicate email addresses crash instead of warning

What we tried: an admin changed one user's email to an address another account already uses.

What should happen: a clear message saying that email is already taken — which is exactly what the "edit my own profile" screen does.

What actually happens: the admin screen has no such check, so the database rejects it and the user sees "Something went wrong on the server."

Priority: low.

B4 — Two full generations of the app's JavaScript are being served

What we found: the public assets folder holds 111 files, with most components appearing two or three times under different build names — Billing three times, the main bundle four times. One of them, Billing-DCOkWAIH.js, is sitting on disk but is not in version control at all.

Why it matters: old versions of pages remain downloadable and can still be reached. One of the old copies is a Settings page that sends a password change without asking for the current password — the server correctly refuses it, so anyone who lands on that old copy gets a silent failure.

Priority: low, but it is a build-hygiene problem worth clearing.

B5 — Live updates go to the wrong client after a ticket is moved

What we found: when a ticket changes hands between clients (see finding 8), the live-update notice is sent using the client the ticket belonged to before the change. The new client's open tabs are never told. Combined with finding 8, the ticket appears and disappears inconsistently across the two portals.

Priority: low.

What is working properly

Worth stating clearly, because a lot of it is done well.

  • Server-side checks are real. We tried more than forty admin requests with no login at all. Every single one was refused. The browser-side page guards are correctly treated as cosmetic — the audit log page will render for any admin, but the server behind it refuses everyone except the super admin.
  • Cross-site request protection works. Every action that changes data requires a token. We sent a delete without it and it was refused.
  • Permissions are re-checked constantly. Change someone's role and it takes effect on their very next request. Change a password and their other sessions are ended.
  • Clients cannot reach across to each other. We tried adding another client's id to the requests for progress, billing and messages. The server ignored it every time and returned the caller's own data.
  • Approvals cannot be run twice. Two admins approving the same request at the same moment resulted in exactly one execution.
  • No leaked secrets. No keys, tokens or private data in the shipped JavaScript. No source maps. The .env file is excluded from version control and has never been committed. Requests for it, including traversal tricks, return the normal app page.
  • Security headers are strong. A solid content policy that blocks inline scripts, HTTPS enforcement, no content-type sniffing, no referrer leakage, and framing restricted to the site itself. The session cookie is inaccessible to JavaScript and marked secure in production.
  • Stripe is handled correctly. Incoming webhooks are signature-checked before anything in them is trusted.
  • The Firestore rules file denies all direct access.

What we could not test

  • The Firestore database option. All live testing ran against the Postgres option. Finding 1 depends on how the database layer maps field names, and the Firestore layer is separate code. Finding 1 must be re-checked there before assuming it is or is not affected.
  • The real ClickUp, Slack, Google Drive, Firebase and Stripe accounts. No credentials were available. One thing to look at when they are: the ClickUp requests glue the id from the web address straight into the outgoing address without escaping it, so a crafted id could bend where the request lands. Admin-only, and confined to ClickUp, but unproven either way.
  • Production network setup. The rate limits count per IP address, which depends on how the live server is configured behind its proxy. Not reproducible from a test harness.
  • An end-to-end version of finding 6. The address poisoning is proven. Actually catching a token from a delivered email was not attempted, as no email service was connected.
  • Heavy concurrency testing beyond the approval race we did run.
