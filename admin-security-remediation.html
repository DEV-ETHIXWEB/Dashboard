Admin Dashboard — Security Remediation

EthixWeb CRM. Follow-up to the audit of 23 August 2026. Admin and staff area only.

Date: 23 August 2026 · Branch deepanshu-branch, working tree on top of commit 35c32b1
Scope: every finding in admin-security-audit.html, plus the class of bug behind each one wherever else it occurred.
Method: each vulnerability was reproduced first as an automated test that asserts the secure behaviour, so it failed before the fix and passes after. Fixes were made at the server enforcement layer. Nothing in production was touched; all testing ran against an isolated in-memory Postgres.
No passwords, keys, tokens, or customer data appear in this document.

1. Executive summary

Everything the audit confirmed has been fixed, with one exception that is reduced rather than removed and is described plainly below. The two critical privilege-escalation paths are closed at three independent layers — the data layer, the route, and the approval queue — so the same class of bug cannot come back through a different field or a different endpoint.

The single most important change is that administrators no longer sign in with a password alone. Every role now completes the same emailed-code step. That one change removes the last rung of the audit's account-takeover chain and, as a side effect, closes the informational finding about the login reply being a role oracle.

That change put the mail transport on the critical path of getting into the building, which raised a fair question: if every admin is signed out and email is not working, how does anyone get back in? They could not have. So each administrator now holds eight one-time backup codes that stand in for the emailed one. They are a replacement for the second factor, not a way past it — the password step still has to be completed first.

Plain summary: an admin can no longer promote itself, cannot touch another administrator's account, cannot read anyone's live sign-in code, and cannot sign in with just a password. What an admin legitimately needs to do — issue client logins, reset a client password, manage tickets and projects — all still works, and is covered by tests that prove it still works.

3. Before / after

Finding 1 · CRITICAL · FIXED
Any admin can make itself super admin by changing the spelling of one word

Before

The user editor refused a body containing isSuperAdmin. It did not refuse is_super_admin, and the database layer accepted both. A trusted admin sent the second spelling and became the owner of the workspace in one request.

Root cause

Not the guard. The guard was fine as far as it went. The cause was one layer below it: objToSnakeEntries in db/setup.js ran every incoming key through toSnake() and matched the result against the column list. That function is a normaliser, so it happily mapped two different spellings onto the same column. Every authorization check in the application written against a camelCase field name therefore had a synonym that walked around it — and the escalation was simply the first place anyone thought to look.

After

Three layers, any one of which stops it.

  • The data layer. A new isWritableField() in db/schemas.js accepts a key only when it is the canonical camelCase name of a real column. isSuperAdmin writes; is_super_admin is dropped on the floor. Both database drivers call it, so the two cannot drift.
  • The route. PUT /api/users/:id no longer copies the body. utils/userFields.js names the eight fields the editor may write; standing is not among them at any spelling, and anything else is refused by name with a 400 rather than silently ignored — a caller aiming at a privilege flag is told where it actually lives.
  • The queue. The stored patch is filtered again at execution time, so a row written by an older build, or edited in the database by hand, still cannot carry a flag into a live account.

Verification

camelCase isSuperAdmin                    -> 400   (was 400)
snake_case is_super_admin                 -> 400   (was 200, promoted)
camelCase adminTrusted                    -> 400   (was 400)
snake_case admin_trusted                  -> 400   (was 200, promoted)
name change + hidden is_super_admin       -> 400   (was 200, promoted)
capabilities afterwards: isSuperAdmin = false

AUTHORIZED  super admin via /standing     -> 200
AUTHORIZED  ordinary name change          -> 200
UNAUTHORIZED trusted admin via /standing  -> 403

Bypass variants were tested on the sibling routes that write the same table: account creation (POST /api/users) and the self-service profile screen (PUT /api/users/me). Neither grants standing at any spelling.

Finding 2 · CRITICAL · FIXED
The approval queue can be tricked into approving a promotion that looks like a name change

Before

A new admin submitted a name change carrying a hidden privilege flag. The queue stored it intact and described it to the approver as "Change their details". An honest colleague clicked approve and the promotion went through.

Root cause

Two failures compounding. The patch was stored unfiltered, so the flag survived into the parked row. And describeUserChange() only knew how to describe the fields it had been taught about — anything else fell into a catch-all phrase. Silence, presented as reassurance.

After

The flag can no longer get into the patch at all — the field allowlist runs before the queue sees it, so there is nothing to disguise. Independently, the summary function was rewritten so that every field in the patch is named, and anything it does not recognise is listed raw rather than swallowed. A future field added to the editor cannot silently become invisible to approvers.

Finding 3 · HIGH · FIXED
An admin can reset the owner's password and is shown the new one in plain text

Before

Any admin could reset any other admin's password, including the super admin's, and read the new password straight out of the response. With admins signing in on a password alone, that was the whole account.

Root cause

The user editor made no distinction between an administrator's account and anyone else's. The app already reserved role and standing changes to a super admin, but the password — the one field that hands the account over outright — was left in the general case.

After

Editing another administrator's account, in any respect and not only the password, now requires whoever is entitled to appoint administrators in the first place. An admin still edits their own account, and a super admin still resets an admin's password when that is genuinely needed. The check is re-run at execution time on the approval path too, in case the proposer has been demoted since proposing.

Finding 4 · HIGH · FIXED
Admins never get a second login step, and the two-step switch does nothing

Before

A branch in the login handler read: if this person is an admin, sign them straight in. Everyone else received an emailed code. The most powerful accounts had the weakest sign-in. Separately, the "Two-step sign in" toggle wrote a value to the database that no part of the login path ever read.

Root cause

A convenience shortcut for the accounts that could least afford one. The toggle was a settings screen with no server behind it.

After

The role branch is gone. Every account — client, employee, admin, super admin — opens a pending session with its password and completes it with an emailed code. That closes the takeover chain: even with a password in hand, an attacker needs the inbox.

The toggle now decides something the server enforces: an account with two-step sign in switched on cannot have a one-tap sign-in link minted for it, and an existing link stops working the moment the switch is turned on. A link is a bearer credential that replaces both factors, so honouring one for an account that asked for two would be the setting lying again in a different way.

Verification

admin password alone            -> 200 {requiresOtp: true}, no session  (was full session)
admin reply vs client reply     -> identical key sets                   (was different)
emailed code completes sign-in  -> 200, full session
one-tap link for a 2FA account  -> 409, refused                         (was 200)
Follow-up to finding 4 · FIXED
The lockout that requiring a code would otherwise have created

The problem this solves

Requiring an emailed code to finish an admin sign-in put the mail transport on the critical path of getting into the building. If mail broke while every administrator happened to be signed out, nobody could get in — and the Login Codes page was no help, because reaching it means already being signed in. Worse, that page deliberately hides administrator codes now (finding 5), so even a colleague could not read one out.

This was not a theoretical concern. It was raised before it could bite, and it is a genuine availability risk created by a security fix.

After

Every administrator holds eight one-time backup codes, in the shape XXXXX-XXXXX, from an alphabet with no look-alike characters because these get read down a phone line.

  • They replace the second factor, not the first. The password step still has to be completed — a backup code is only accepted against a session that has already proved the password. A code on its own is refused.
  • Only the bcrypt hash is stored, so the table is not a list of working credentials, and the server genuinely cannot re-display them. They are shown once: on the Security page when generated, and alongside the temporary password when a new administrator is created.
  • One use each, and generating a new set immediately invalidates every earlier code.
  • Using one is announced to every other administrator and written to the audit log. A break-glass event that happened quietly would be worse than no record at all.
  • They are for administrators only. Everyone else has an admin who can read their code off the Login Codes page; an admin has nobody, which is the entire reason these exist.
  • They follow the role. A demoted administrator's codes are deleted with the demotion.

Verification

24 automated checks, plus the whole scenario driven by hand through the real built UI: the mail transport was killed outright, the administrator signed out, and the way back in was a backup code and nothing else.

admin signs in with password    -> "We could not email your code"

the other admins are notified; the audit log records via: recovery_code

EXPLOIT BLOCKED  a spent code, reused                -> 403
EXPLOIT BLOCKED  a code after the set was replaced   -> 403
EXPLOIT BLOCKED  one admin using another's code      -> 403
EXPLOIT BLOCKED  a code with no password step first  -> 401
UNAUTHORIZED     a non-admin asking for codes        -> 403

One thing to do. Backup codes protect an administrator who has generated a set, and the existing administrators start with none. The Security page says so in the strongest terms it can, but it cannot make anyone click. Tell your admins to generate theirs today rather than on the day they need them — or issue the first set for them with the tool below.

Follow-up · FIXED
The first administrator, on a deployment where mail has never worked

The problem this solves

Backup codes cover an administrator who has generated a set, which requires having signed in at least once. That leaves one case uncovered: a deployment where mail has never worked and no administrator has ever completed a sign-in. Nobody holds a code, and nobody can generate one, because generating one means being signed in. The front door is shut with everybody outside it.

After

A command-line tool, run on the server, issues a fresh set of backup codes for one named administrator:

npm run admin:recovery -- list
npm run admin:recovery -- issue admin@example.com --reason "mail transport down" --yes

The design question worth answering plainly is whether this hands anyone new power. It does not. Anyone who can run this can already reach the database and rewrite a password hash by hand. What the tool adds is a supported way to do it that leaves a record — the hand-edited database row leaves none.

  • It refuses anything that is not an administrator. A locked-out client or staff member has an admin to help them; that is a different and much smaller problem, and not a reason to build a second way into their account.
  • It never touches a password and never prints one.
  • Nothing happens without --yes. The bare command is a dry run that names the account, says how many codes it holds, and states exactly what would change.
  • It is on the record twice — an audit entry marked issued_from_server, carrying whatever reason was given, and an in-app alert to every other administrator saying a set was issued from the console and to treat it as a security event if unexpected.
  • The codes it issues are ordinary ones. Same shape, same one-time use, same replacement rules, verified through the normal sign-in path.

Verification

20 automated checks, plus the tool run as a command against a throwaway database.

issue <admin>   (no --yes)            -> dry run, nothing changed

unknown command                       -> usage, exit 1

Finding 5 · HIGH · FIXED
Any admin can read anyone's live login code, and see everyone's IP address

Before

Both endpoints checked only that the caller had the admin role. A five-minute-old, untrusted admin could list every recent sign-in attempt with name, email and IP address, and decrypt anybody's six-digit code — enough to finish someone else's sign-in.

Root cause

A role check where an authority check was needed, and no notion at all of whose code was being read.

After

Three separate constraints, because the page has a legitimate purpose worth keeping:

  • Administrator codes never appear on the page and can never be revealed, by anyone, including a super admin and including the code's owner. Admins now sign in with a code, so revealing one would undo the second factor rather than support it.
  • Revealing any other code requires a trusted admin — someone the workspace has actually vouched for.
  • IP addresses are shown to a super admin only. Everyone else sees hidden. A person's rough location and movements are not part of "help this client sign in".

Every reveal is written to the audit log with the target and their role, the account whose code was read is notified in-app, and the endpoint has its own rate limit.

Verification

untrusted admin lists codes        -> 200, but every ipAddress is "hidden"
any admin row in the list          -> absent
untrusted admin reveals a code     -> 403                    (was 200 + code)
super admin reveals an admin code  -> 403                    (was 200 + code)

AUTHORIZED  trusted admin reveals a client's code -> 200 + code
rate limit                                        -> 429 within 25 attempts
Finding 6 · HIGH · FIXED
The app learns its own web address from whoever talks to it first

Before

With APP_BASE_URL unset, the app took its own origin from the first request after a restart and kept it for the life of the process. That address was glued onto the one-tap sign-in links in client welcome emails. An attacker reaching a freshly restarted server first, with an Origin naming their own site, had every subsequent welcome email carrying a working login link pointed at them.

Root cause

A convenience fallback that treated an attacker-controllable header as configuration.

After

A learned origin now has to be one the operator already named — APP_BASE_URL itself, or an entry in CORS_ORIGINS. A header cannot nominate a new one. Outside production a loopback or private-LAN origin is also accepted, because that is the Vite dev-proxy case this behaviour existed for; a publicly reachable address is never learned from a header in any environment.

When nothing is configured and nothing is learnable, baseUrl() is empty and the callers that build links already treat that as "send the credentials without a one-tap link" — a degraded outcome, but a safe one, and the server now says so at boot instead of leaving it to be discovered.

Verification

Origin:  https://evil.example.net  -> baseUrl() unchanged   (was poisoned)
Referer: https://evil.example.net  -> baseUrl() unchanged   (was poisoned)
Host:    evil.example.net          -> baseUrl() unchanged   (was poisoned)
Mail page · HIGH · FIXED
Every email is stored in full, and every admin can read it

Before

The Mail page kept each outbound message with its complete HTML body. A client welcome email contained the plaintext temporary password and a working one-tap sign-in link. A brand-new untrusted admin could open it and read both. In practice the page was a permanent, browsable store of live credentials.

Root cause

A good idea applied without exception. Storing the body is right for a ticket update and wrong for a credential, and the logger did not distinguish.

After

The bodies of the two credential-bearing templates — credentials and login_code — are no longer stored at all. The row itself remains, because who it went to, when, and whether it was delivered is what the Mail page is for; the page already renders "logged without a stored body" for such rows. As a second measure, any sign-in token that finds its way into any other template's body is redacted before storage, so a future email cannot reintroduce the problem.

Verification

stored credentials email contains the temporary password -> no  (was yes)
stored email contains a usable magic-link token          -> no  (was yes)
stored login-code email contains a six-digit code        -> no  (was yes)

AUTHORIZED  the link is still minted, still works, still single-use
AUTHORIZED  only the SHA-256 of the link secret is ever stored

Finding 8 · MEDIUM · FIXED
Any employee can edit or reassign any ticket, including moving it to a different client

Before

Admins, project managers and employees were one bucket called "staff", and the whole request body was copied onto the ticket. An employee with no connection to a ticket could alter it, close it, or move it into another client's portal.

Root cause

Two things: a role grouping that flattened three different levels of authority, and a wholesale body copy that included the field deciding which portal shows the record.

After

An employee may edit only the tickets that are theirs — assigned to them, or one they were brought onto as a collaborator. Admins and project managers still see the whole queue, which is their job. Moving a ticket between clients is an administrator's decision, and the destination has to be a real client account. createdAt joins the ClickUp fields as immutable.

The same class was swept for and fixed on projects and domains, which copied their bodies the same way. Ticket edits now also record which fields moved, and a change of owner notifies both portals rather than only the old one — which was defect B5.

Verification

Finding 9 · MEDIUM · PARTIALLY FIXED
An admin can create a sign-in link for a client and use it themselves

Before

Any admin, including a brand-new untrusted one, could mint a link and simply open it. It worked for up to seven days. The only trace was a single line saying a link had been issued; everything done afterwards was recorded as the client's own activity.

Root cause

This is a real, wanted feature, and a link is a bearer credential by construction — whoever holds it is the client. The exposure was not the link but the absence of any constraint on who could mint one and any signal that one had been used.

After — and what remains

Three things changed, and one thing did not.

  • Minting a link now requires a trusted admin, so a fresh account cannot do it at all.
  • The client is notified in their own portal the moment a link is issued for their account, with an invitation to say so if they did not ask. A silent tool becomes a visible one.
  • The resulting sign-in is attributed: the audit row for the login names the admin who minted the link, so the trail no longer reads as the client signing themselves in.
  • The endpoint has its own rate limit, and an account with two-step sign in switched on cannot have a link minted at all.

What remains: a trusted admin who mints a link can still open it themselves and act as that client for the life of the link. Removing that would mean removing the feature, which the audit explicitly warns against and which support genuinely uses. The risk is now bounded to vouched-for accounts, visible to the client, and attributable after the fact — but it is not eliminated, and it is marked partially fixed for that reason.

Verification

2FA-enabled account           -> 409                    (was 200)

AUTHORIZED  trusted admin mints a link  -> 200 + path
the client receives a security notification

Finding 11 · LOW · FIXED
The session identifier is not replaced after the login code is entered

Before

Entering the code upgraded the session that already existed. The identifier held while the person was still unauthenticated carried on afterwards.

Root cause

promoteSession() flipped a flag in place instead of issuing a new session.

After

Finding 12 · LOW · FIXED
Uploaded files are not checked, and SVG images are displayed from the app's own address

Before

There was no list of allowed types. Whatever the uploader claimed was stored and handed back under that label. SVG was on the inline-render list, so an uploaded SVG was displayed inside the app. The content-security-policy header was the only thing preventing the script inside it from running.

Root cause

No validation at the boundary, and a rendering decision that trusted a caller-supplied label. One header away from code execution is not a boundary.

After

An explicit allowlist of thirteen document and image types, each with the extensions it is permitted to wear. Both halves must agree, so a .js file announced as a PDF fails on the second test after passing the first. SVG is off the inline list entirely. Rows uploaded before the allowlist existed are served as neutral downloads rather than under their own label, so nothing already in storage can be coaxed into rendering. The upload also verifies the named client is a real client account.

Verification

.js named file sent as a PDF   -> 415  (was 201)

AUTHORIZED  a genuine PDF uploads               -> 201

Defects B1, B2, B3, B5 · FIXED
The approved path now does what the direct path does

Before

An account created through the approval queue lost its Slack channel and never received its credentials — the password existed only in a hash, so nobody on earth knew it and the account was unusable. An approved password reset had the same problem. A duplicate email address crashed with a 500 instead of the clear message the profile screen gives.

Root cause

Two implementations of "create an account": the real one in the route, and a shorter copy inside the queue that had drifted. The credentials email was only ever wired into the first.

After

One implementation, in utils/userProvisioning.js, used by both callers. The queue now writes every field the proposal carried, adds the bot to the Slack channel, and sends the credentials.

A generated password on the approval path is minted at execution time and emailed to the account it belongs to, rather than being parked in the queue as plaintext until somebody signs it off. An explicitly chosen password is hashed immediately, since the admin already knows it. That fixes the delivery defect and closes N2 in the same move: nothing secret waits in the queue.

The duplicate-email check the profile screen always had is now on the admin editor too, answering 409 with the same sentence.

The security suite (scripts/security-regression.js, run with npm run test:security) was written before any fix was made. Every check asserts the secure behaviour, so the first run against the unremediated code was a reproduction of the audit: 40 of its 98 checks failed, matching the audit's findings one for one. 5. Remaining findings

Nothing here is hidden or downgraded. These are the things that are not fully closed.

PARTIALLY FIXED — Finding 9, admin-issued sign-in links

A trusted admin who mints a client sign-in link can still open it themselves and act as that client until it expires. This is inherent to a bearer credential and cannot be removed without removing the feature. It is now restricted to vouched-for admins, announced to the client in their portal, attributed in the audit log, rate limited, and refused outright for accounts with two-step sign in switched on. Consider whether the feature should require the client to confirm before the link becomes usable — that would close it fully, at the cost of the thing that makes it useful.

OPEN — Five moderate dependency advisories

The uuid package and its dependants under firebase-admin carry a moderate advisory. Fixing it requires a breaking major upgrade of uuid and, transitively, of firebase-admin — which Phase 19's own rule says not to do as part of a security fix unless it materially affects the vulnerability.

Reachability: the advisory concerns a missing buffer bounds check in the v3, v5 and v6 generators when the caller supplies a buffer. This codebase imports { v4 } and nothing else, in all eight places it uses the package, and never passes a buffer. The advisory is not reachable from application code. The high-severity brace-expansion advisory, which was reachable, has been fixed. Schedule the firebase-admin major as ordinary maintenance.

FIXED — Defect B4, two generations of frontend JavaScript

Resolved as a side effect of the work this change required. The backup-codes feature needed a new screen, so the frontend was rebuilt, and npm run build wipes public/ before copying fresh output. The folder went from 111 asset files to 85, with one copy of each component instead of three; the untracked Billing-DCOkWAIH.js went with it. The stale Settings bundle the audit named is no longer served.

Two consequences of that rebuild worth knowing about. sw.js is now present in public/ for the first time — the application has always tried to register a service worker and the file was simply missing, so this is the intended behaviour arriving rather than something new. And returning visitors will fetch new asset filenames on their next load, which is normal for a deploy.

UNVERIFIED — Rate limiting behind the production proxy

All limits count per IP address. app.set('trust proxy', 1) is set in production, which is correct for a single trusted proxy in front of the app. Whether the production chain is in fact one hop cannot be established from a test harness. Confirm it against the live deployment; if there is more than one proxy, the value needs to match.

UNVERIFIED — The Firestore deployment

All live testing ran against Postgres, as the audit's did. The escalation hole the audit flagged as unknown for Firestore was present, and is fixed by routing both drivers through one shared field gate — which is unit-checked, and the driver is asserted to call it. That is fixed by construction, not by live exploitation. If Firestore is or will be used in production, re-run the security suite against it once credentials are available.

UNVERIFIED — ClickUp path handling

Identifiers taken from the browser's URL are now percent-encoded before being interpolated into ClickUp request paths, and any path containing .. is refused. No ClickUp credentials were available, so this is fixed by inspection and not proven against the live API. Re-test when a token is available.

Accepted residual risks

  • An admin can still reset a client's or staff member's password and read it on screen. This is the design — the admin hands the credentials over — and the audit did not ask for it to change. It is now bounded: never against another administrator, rate limited, audited with the field list, and it ends every existing session of the target.
  • The Mail page still shows every non-credential email to every admin. That is what the page is for, and the two templates that carried secrets no longer store their bodies.
  • Administrator sign-in depends on a working mail transport, or a saved backup code. Mail is configured on this deployment and the server warns loudly at boot if it ever is not. Every administrator should generate their backup codes from the Security page now rather than at the moment they are needed — the page says so, but it cannot make anyone do it.
  • Server access can still mint entry to any administrator account, through the break-glass tool. That was already true of anyone with database access, and the tool makes it recorded rather than silent — but it is worth being clear that shell access to this server is equivalent to administrator access to the workspace, and should be treated that way.
