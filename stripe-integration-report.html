Stripe Billing — Setup, Repairs and Verification

EthixWeb CRM. Client payment history, mirrored from Stripe and managed by an admin.

27 August 2026 · Branch main at commit 53f825b · 8 files changed, 471 lines added
Asked for: connect the live Stripe account, load payment data per client, let an admin manage it, prove it works.
Verified by: 38 automated checks driving the real app against the live Stripe account on a throwaway in-memory database, plus a manual pass through the admin screen. No production record was written; no key is printed here.

The short version

The Stripe code was already written, and it was good code. It had never been run against a real Stripe account, and three faults stopped it working at all. All three are fixed, plus a fourth that was quietly getting the money wrong: every invoiced payment was counted twice. A client who had paid $4,750 would have been shown $9,500 — two stored rows for one payment, not a display problem.

Plain summary: Stripe is connected, an admin can say which Stripe customer belongs to which client, and each client's real history loads on their page. Totals now match the Stripe dashboard to the cent for all five customers — $2,196 · $4,000 · $4,750 · $260 · $4,750.

What was fixed

Fault 1 of 4 · Critical · Confirmed
Every invoiced payment was counted twice

One payment appears in Stripe as two objects — an invoice and the charge that paid it. The app skipped the charge if it named its invoice, but current Stripe API versions no longer fill that field in, in either direction. The skip never happened, so both were stored. Asking Stripe directly for one customer:

invoices marked paid  = $4,750
charges succeeded     = $4,750   (the same five payments)
what the app stored   = $9,500   (all ten rows)

Fix: an invoice and its charge share a payment intent. That id is now saved with every payment row, and a second view of the same money merges into the existing row instead of adding another. The invoice keeps the description, number and PDF link; the charge contributes card brand and last four digits. Neither is lost.

Fault 2 of 4 · High · Confirmed
"Sync from Stripe" failed for every client, every time

The subscription request asked Stripe to expand data.items.data.price.product — five levels deep. Stripe permits four and rejects the whole request: "You cannot expand more than 4 levels of a property." This is the repair button for a webhook that never arrived, and it had never once succeeded against the live account.

Fix: ask for four levels, fetch the product name in one extra request. If that request fails the sync still completes, falling back to the price nickname.

Fault 3 of 4 · High · Confirmed
No client could ever be matched to a Stripe customer

The only pairing rule was "their email addresses happen to be identical". Not one of the three client accounts matched any of the five Stripe customers, so every client would have shown an empty payments page forever, with no way for an admin to correct it. Worse: two companies — Gary's Pipelining and All Phase Plumbing — share one contact address, and the old code took whichever Stripe returned first, so a match could have shown a client another company's history.

Fix: the pairing is stated by an admin, not guessed. A new admin-only control lists every Stripe customer and files a client under one, importing that history immediately. A genuinely ambiguous email now says so instead of picking one.

Fault 4 of 4 · Medium · Confirmed
A payment could arrive with no receipt email

Introduced by the fix for fault 1 and caught before it shipped. Stripe does not guarantee event order; if a charge notification arrived before its invoice, the merge made the invoice look like a repeat of something already recorded — and repeats deliberately send no email, so that client would silently never be thanked.

Fix: the merge reports when an invoice folds into a charge for the first time, which counts as a first sighting. A genuinely replayed notification still sends nothing.

What was added

Every client account is now listed on the Payments page, including clients with no Stripe link — who need attention and previously did not appear at all. Each row offers a dropdown of the real Stripe customers (choosing one imports that history and reports how many payments came in; Not linked unlinks) and a View button that narrows the page to that client and points the sync button at them. Moving a customer between clients releases the first client's rows in the same step, so two clients can never show the same money. Unlinking detaches the payment records but keeps them — they are Stripe's history.

Who sees what: a client sees only their own history and can neither list customers nor link anything; an admin sees the whole workspace or one client and does the linking and syncing; sales, project managers and employees see no billing at all.

The customer list is admin-only on purpose — it names every customer of the business. A client requesting it directly is refused, as is a client trying to link themselves; both were tested as real requests, not assumed from a hidden menu.
