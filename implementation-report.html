What a delivery does, in order

1Admin picks a moment. One row is written; picking again moves it rather than queueing a second.
2A sweep finds it due and claims it atomically.
3A token is minted now, so its clock starts when the email lands — not when the delivery was booked.
4The email goes; the row reads Sent. A failure retries twice, then parks and alerts the admins.
5The recipient sets a password nobody here ever learns.

2Configuration you must fix

Three faults were found on this machine. None is in the code; all three are why nothing appeared to work.

1. Your SMTP2GO key is rejected. Verified with a read-only call: "SMTP2GO refused our credentials." No email works at all — not the new ones, not sign-in codes, not ticket alerts. Replace SMTP2GO_API_KEY with a live key.

2. APP_BASE_URL is not set — and neither is CORS_ORIGINS. The app deliberately refuses to learn its own address from a request header unless one of those already names it, so an attacker cannot point welcome-email links at their own server. With neither set the address is permanently unknown, and an activation or reset link is the whole email — so both features fail rather than degrade. Set APP_BASE_URL=https://your-domain and restart.

3. public/ had never been built. It is gitignored build output, and npm start serves the frontend from it — so with no public/ the app renders nothing whatsoever. Fixed: npm run build has been run and the folder now holds all four features.

Because fault 2 is silent and expensive, it is now loud in two places: the boot log states plainly that scheduled deliveries will fail without it, and the delivery dialog shows a "this will fail" banner before a date is chosen rather than booking a failure for later.

New optional settings are documented in .env.example: password age, warning window, minimum length, link lifetimes, whether the job timers arm, and where avatar bytes live. Every one has a working default.

5Scheduled jobs

Built in the pattern this codebase already uses (slaWatch, domainWatch) rather than adding a queue: the app targets serverless, where a setInterval at boot is a scheduler on a laptop that silently does nothing in production.

credential
Scheduler		Finds due deliveries and sends them.
password
Watch		Warns before expiry; flags and emails a reset link after it.

Each runs three ways: on admin request traffic (throttled to one pass per interval), from a Check credentials button on the Mail page, and from a real timer on any host that keeps a process alive — so a 3am delivery does not wait for the first sign-in.

Duplicate emails are impossible, not unlikely. A delivery is taken by an atomic scheduled → sending claim, so two instances sweeping at the same moment means exactly one of them sends. A claim whose process died is released after 15 minutes. Failures retry twice with backoff, then park as Failed and email the administrators.

7Security

  • Tokens are stored hashed (SHA-256 of a 32-byte secret), compared in constant time, single-use through a conditional update, and expiring. Copied from the existing sign-in-link design rather than invented.
  • Links travel in the URL fragment (#token=), which browsers never send to a server — so a token cannot reach an access log or a Referer header, and a link-scanner cannot burn the single use.
  • Passwords stay bcrypt, via the app's existing hashing. Every write is routed so the age stamp cannot be forgotten — including down the approval queue.
  • A reset destroys every session of that account, plus outstanding links and live sign-in codes.
  • No user enumeration: the forgot-password endpoint returns a byte-identical answer for a known and an unknown address (asserted in the tests).
  • Uploads are judged on their bytes. Filename and declared type are ignored entirely; format and dimensions are read from the file header. SVG, HTML and oversized files are refused, and the type a file is served as is the one the validator decided.
  • Nothing sensitive is logged — no password, token or hash appears in an audit row, error or email log.
  • Admin-on-admin rules preserved: scheduling or retrying another administrator's credentials remains a super admin's alone.

Pre-existingThe security suite was already failing: 69 passed, 32 failed, then crashed. One stale expectation — it wanted a super admin to receive a peer admin's regenerated password, which the code deliberately withholds — cascaded into 30 downstream failures. The test was corrected to assert the secure behaviour; the control was not weakened.

Checking it yourself

Once a live mail key and APP_BASE_URL are in place, the fastest honest test is about four minutes:

  • Client Access → Delivery on any client → pick In an hour, then edit the time to a minute ago → Schedule.
  • Mail → Check credentials. It reports what it sent. The row turns Sent.
  • Open the email, follow the link, set a password. The link dies on second use.
  • Sign in with it. The confirmation email should already be waiting.

To see the expiry wall without waiting a month, start the server with PASSWORD_MAX_AGE_DAYS=0.00002 — every password ages out in under two seconds. That is exactly how it was verified here.

12Limitations

  • Phone number and department are not on the profile. The schema has neither, and inventing columns you may model differently was the wrong call. Say the word and they are a short change.
  • Avatars resize in the browser, not the server. A server-side resize means a native image library, which breaks a serverless bundle. The server still validates every byte; it just does not repair a bad file. utils/avatarStore.js is a driver seam for object storage later.
  • The Firestore path is written but not exercised against a live Firestore, as this deployment runs Postgres.
  • Password rotation defaults to on at 30 days. Existing accounts start their clock at first boot after the migration, so nobody is locked out; set PASSWORD_POLICY_ENABLED=false to disable.
